# 練成画像の読み取り（8bit）

モンハンライズ：サンブレイクの「傀異強化結果」画面（Switch のスクリーンショット）から、
防御力・スロット・火〜龍耐性・スキルとレベル・所持ゼニーを読み取り、NX Macro Controller の
result_log と同じ形式にする。取込タブの「練成画像から取込」から実行でき、バッチの取込元は `8bit` になる
（テキストの取込は `nx`）。元は別リポジトリ mhrise-skill-ocr で開発していたもの。

## ファイル

| ファイル | 役割 |
|---|---|
| `app/ocr/kuijin_ocr.py` | 本体。テンプレート照合で読み取り、取込形式の結果と自己チェックのエラーを出す。CLI としても使える |
| `app/ocr/image_import.py` | 取込タブから呼ぶ。フォルダを読み取り、取込元 `8bit` のバッチとして保存する |
| `app/ocr/spec.py` | 抽選の仕様のチェック（仕様違反）と、結果画面２の写っていないスキルの判定 |
| `app/ocr/template_sync.py` | アプリが使う見本（複製）を、同梱の見本の更新に追従させる |
| `app/ui/ocr_label_dialog.py` | 取込タブで、ラベルが確定していない見本の正しいラベルをユーザーに選んでもらうダイアログ |
| `app/ocr/templates/` | 読み取りの見本（テンプレート）とラベル。**読み取りの正しさそのもの。消さない** |
| `app/ocr/templates/review/` | 見本の拡大画像（確認用。flet build の除外はプロジェクト直下の名前にしか効かないため、配布物にも入る。約 3.6MB） |
| `scripts/ocr/pick_images.py` | 指定スキルのレベルが上がった画像を抜き出す |
| `scripts/ocr/spot_check.py` | ランダム抜き取り確認用の一覧画像を作る |
| `scripts/ocr/check_spec.py` | 結果が抽選の仕様で作れるかを調べる（判定はアプリと同じ `app/ocr/spec.py`） |

スキル名とコストの一覧は `app/core/skill_master.py` を共有している。

## 見本の置き場所

- CLI（`python -m app.ocr.kuijin_ocr`）は既定で同梱の `app/ocr/templates/` を読み書きする。
  ラベルを付けた見本はここに入れてコミットし、配布物に同梱する
- アプリは `%LOCALAPPDATA%\QuriousCraftingLog\ocr_templates\` を使う（インストール先には書き込めないため）。
  初回に同梱の見本を複製し、複製したときの同梱の見本の数を `bundled_manifest.json` に記録する
- アプリの更新で同梱の見本が増えていたら、画像取込のときに組み直す（`template_sync.py`）:
  新しい同梱の見本（開発側のラベルの修正を含む）の後ろに、ユーザーがラベル入力で付けた見本のうち
  同梱と一致しないものを足す。同梱に新しくできた見本の種類・画面判定の見本も足し、
  スキルの性質（`skill_props.json`）は同梱の値を優先してまとめる
- 対応している解像度は、見本のフォルダにその解像度のスキル名の見本（`{解像度}_name.json`）があるもの。
  それ以外の解像度の画像が 1 枚でもあると、取込は読み取りの前に中断する（JPEG のヘッダーだけ調べる。7,500 枚で約 0.3 秒）

## 環境

- 実行時の依存は numpy / opencv-python-headless（`pyproject.toml` の dependencies）
- 開発用の optional-dependencies `ocr-dev` は Pillow だけ（`spot_check.py` と `--slot-sheet` で使う）
- EasyOCR は使わない（下記「EasyOCR による検算の終了」）
- Windows。Python は `PYTHONIOENCODING=utf-8` を付けて実行すると日本語の出力が化けない
- 画像の切り出しは、ソースから起動したときは別プロセスで並列に、exe 版ではスレッドで行う
  （exe 版で子プロセスを起こすとアプリ本体が起動するおそれがあるため。7,500 枚で約 12 秒 → 約 26 秒）

## 1 バッチの検証手順（開発用、リポジトリ直下で実行）

例: `d=samples/base_slot6/0926_2`（初期スロット 6、4000 ゼニー、マッスル）

新しい防具の最初のバッチも、この手順で確認する（「EasyOCR による検算の終了」を参照）。

1. 読み取り
   ```
   .venv/Scripts/python -m app.ocr.kuijin_ocr --base-slot 6 --zenny-step 4000 --minus-skills 攻撃:2,火事場力:3 --table 5 $d -o ${d}_result.txt --detail ${d}_result.csv
   ```
   `--minus-skills` は防具が元から持つスキルと元のレベル（マッスルアームは `攻撃:2,火事場力:3`）。
   それ以外のスキルが下がった・元のレベルより多く下がったら自己チェックのエラーになる。結果画面２の写っていない
   スキルの判定にも使う。`--table` を付けると仕様違反もエラーのファイルに書く。他の防具では指定を変える
2. 画像の抜き出し（**ユーザーには最初にこれを渡す**）
   ```
   .venv/Scripts/python scripts/ocr/pick_images.py ${d}_result.csv $d -s 龍気変換 奮闘 激昂 業鎧修羅 狂竜症蝕 -o ${d}_picked
   ```
   新しいスキル名の見本に対象スキルが含まれていれば、画像で確認してから渡す
3. 新しい見本に名前を付ける（下記）→ 1 を再実行して check 0 件にする → 2 も再実行
4. 仕様チェック（1 で `--table` を付けていれば不要）
   ```
   .venv/Scripts/python scripts/ocr/check_spec.py --table 5 --minus-skills 攻撃:2,火事場力:3 ${d}_result.csv -o ${d}_spec_errors.csv
   ```
5. 抜き取り確認（60 枚、結果画面２とレア演出を含む）。一覧画像を全部見る
   ```
   .venv/Scripts/python scripts/ocr/spot_check.py ${d}_result.csv $d -n 60 -o samples/spot/{バッチ名}
   ```

## EasyOCR による検算の終了

EasyOCR（別の方法での読み取り）による全件検算は 0926_4 で終了し（2026-09-26）、検算スクリプトと
EasyOCR による見本の自動ラベル付けは削除した（2026-09-30、ユーザー了承）。
9 バッチで kuijin の誤りは 0 件（食い違いはすべて EasyOCR 側）だった。

- 検算が見ていたのは、スキル名・防御力・耐性・レベル・ゼニーの読み取り。これらは画面の描き方
  （フォント・位置・演出）に依存し、防具には依存しない。スキル名の見本は全 123 スキルそろっている
- 防具を変えて変わるのは「初期スロット」と「初期スキルとその値」だけ。スロットは検算の対象外だった
- 画面の描き方が変わる状況（ゲームのアップデート、Switch の表示設定・解像度、撮影方法の変更）は
  起こらない前提とした（ユーザー判断）。別の解像度の画像は取込時にエラーにする

新しい防具の最初のバッチでは、代わりに次を行う:
1. 取込タブで「防具が元から持つスキル」を正しく入力する（それ以外のスキルが下がっていたら自己チェックの矛盾になる）
2. 新しい初期スロットではスロットの見本がすべて新しくなるので、ラベル入力のダイアログで慎重に付ける
3. 抽選の仕様チェック（`check_spec.py`、アプリでは取込時の「仕様違反」）を通す
4. 抜き取り確認（`spot_check.py`、60 枚）

## 見本（テンプレート）の名前付け

実行時に「新しい〇〇テンプレート N 個」と表示される。`app/ocr/templates/review/1280x720_{種類}/` の画像を見て、
`app/ocr/templates/1280x720_{種類}.json` の該当番号（0 始まり、上から順）にラベルを書く。

| 種類 | ラベル |
|---|---|
| `glyph`（防御・耐性の 1 文字） | `"0"`〜`"9"`、`"+"`。演出の粒などのノイズは `""` |
| `money_glyph`（ゼニーの 1 文字） | `"0"`〜`"9"`。ノイズは `""` |
| `slot_base{N}` | 追加スロット数 `"+0"`〜`"+6"`。`--slot-sheet 画像.png` を付けて実行すると色付きの確認画像が出る |
| `name`（スキル名） | スキル名（`app/core/skill_master.py` の表記）。「雷」と「龍」のように似た文字に注意して画像で確認する |
| `value`（防御・耐性の値） | glyph から自動で組み立てるので編集不要 |

新しい見本はほとんどがレア演出（赤く光る画面）か、結果画面２・2〜3 行目のスキル名のわずかな描画差によるもの。

## アプリでのラベル入力（取込タブ）

画像取込は「切り出し・照合（`start_reading`）→ ラベル入力 → 結果の作成（`finish_reading`）→ 取込」の順に進む。
ラベルが確定していない見本（`TemplateBank.is_unlabeled`: 未設定・スロットの `?slot#n`・スキル名の `…?`）があると、
取込タブでダイアログを出し、画像を見て正しいラベルを選んでもらう。

| 種類 | 表示する画像 | 選択肢 |
|---|---|---|
| スキル名 | 元画像のスキル名の行（カラー） | skill_master の全スキル（文字入力で絞り込み） |
| 追加スロット数 | 元画像のスロット欄（カラー） | `+0`〜`+6`（初期スロットからの増加数） |
| 防御力・耐性の文字 | その文字を含む欄（カラー、文字を赤枠で囲む。`locate_glyph`）と、二値化した 1 文字 | `0`〜`9`・`+`・ノイズ（`""`） |
| 所持ゼニーの文字 | 所持ゼニーの欄（カラー、文字を赤枠で囲む）と、二値化した 1 文字 | `0`〜`9`・ノイズ（`""`） |

- 入力画面: すべての見本のラベルを選ぶまで「入力したラベルで続ける」は押せない（「?」の行を作らないため）
- 確認画面: 画像と選んだラベルを並べて表示する（変更不可）。「この内容で確定」でラベルを付けて見本を保存し、
  取込に進む。「戻って修正する」で入力画面に戻る
- 「取込を中止」（どちらの画面にもある）: 何も保存しない（見本も保存しない）。初期スロットの入力ミスなどで
  見本がたくさん出たときや、判断できない見本があるときに使う
- 付けたラベルは `%LOCALAPPDATA%\QuriousCraftingLog\ocr_templates\` の見本に保存され、次回から使われる。
  同梱の見本（`app/ocr/templates/`）には反映されないので、配布物に入れたいときは開発側でラベルを付け直す
  （同梱の見本を増やしても、ユーザーが付けた見本はアプリの更新後も残る。「見本の置き場所」を参照）

## 仕様・決めたこと

- レベルの増減は "Lv +n" の文字ではなく、スキル名の下の四角の色を数える（緑 = +1、赤 = -1）。
  文字がオレンジ = 最大レベル到達、緑 = 空きあり（全データで例外なし）
- コスト = 6 × 追加スロット + Σ（上がったスキルのコスト × 上がったレベル）。**耐性のコストは含めない**
  （画面は合計しか出さず一意に決まらない。仕様の制約を使っても一意なのは約 15%）
- 結果画面２（「◀ L 1/2 R ▶」がある画面、4 つ目以降のスキルがある）は 25 画素下にずれる。
  4 つ目以降は写っていないので、出力では第 4 名に印を書く（下記「結果画面２の写っていないスキル」）
- スキルの表示順（ユーザー確認済み、base_slot6 の 99,364 枚でも例外なし）: プラスのスキルはコストの高い順
  （同じコストどうしの順番はランダム）、マイナスのスキルはプラスの後ろ。
  結果画面２の隠れた 4 つ目以降は「3 つ目以下のコストのプラス」か「マイナス」に限られる
- 防具に付くスキルは、元から持つスキルを含めて 5 種類まで（ユーザー確認済み）。元から持つスキルのレベルが
  0 になっても数える。マッスル腕・ギルパレ脚は元から 2 種類なので、それ以外のプラスは 3 種類まで。
  元から持つスキル自体がプラスになることはある（種類は増えない）
- 抽選の仕様（hyperWiki のテーブル）: 最大 6 回、確率 0 の項目と「不明」は出ない、最後に残りコストを防御力に変換
  （変換は防御力を上げるだけ）。
  **仕様のチェック（`app/ocr/spec.py`）では防御力の値を使わない**: テーブル 6 の 33 枚（aaaa 31・bbbb 2）が、
  防御力の変換の規則を外しても説明できず、防御力の項目そのものが実際の抽選と合っていないため。
  代わりに「防御力の結果がマイナスなら、防御力マイナスの項目を 1 回以上引いている」だけを使う。
  この形で、これまでの全データ 125,369 枚（テーブル 5・6）が仕様で作れる（仕様違反 0 件）
- ユーザーが確認済みの抽選の事実: 同じコストのスキルは等確率、耐性は 5 属性に等確率で重複あり、
  スキル -1 は防具が元から持つスキルから等確率。マッスルアームで下がるのは攻撃（元 Lv2）と火事場力（元 Lv3）だけ
  （base_slot6 の 88,720 枚でも例外なし）。未解明: 残りコストより高い項目が出たときの扱い、6 回未満で終わる条件

## 出力形式（`*_result.txt`、UTF-8。取込タブのテキスト取込と同じ形式）

```
初期ゼニー,52928
回数,ゼニー,スロ,コスト,マイナス,耐性,第1名,第1値,…,第6名,第6値,対象
```
ゼニーは千単位。回数はゼニーから求め、同じ回の重複は読めている画像を優先して 1 枚残す。
耐性は火〜龍の合計。マイナスはレベルが下がったスキルの有無。対象は 0 固定。

取込時の扱い（`app/core/parser.py`）:
- 結果画面２の行は、第 4 名の印（下記）を値 0 のスキルとして記録して取り込む。値 0 なので
  スキル集合検索のしきい値判定には影響しない。印はスキル集合管理では選べない
- 読めなかった値（`?`）を含む行は「読み込みできなかった行」になる（実在しないスキル名を登録しないため）
- 自己チェックのエラーはバッチのエラーの「画像読み取りの矛盾」、抽選の仕様で作れない結果は
  「仕様違反（要確認）」に入る（仕様違反は抽選テーブルが「なし」の防具では調べない）

## 結果画面２の写っていないスキル

`app/ocr/spec.py` の `classify_hidden` で判定し、第 4 名に次の印を書く。

| 判定 | 印（値 0） | マイナス（スキル欠け） | 検索結果の内訳 |
|---|---|---|---|
| すべてマイナス | `何らかのマイナススキル` | 有 | 何らかのマイナススキル |
| マイナスが 1 個以上 | `不明（マイナススキルが一個以上）` | 有 | 不明（マイナススキルが一個以上） |
| 分からない | `不明` | 写っている分から判定 | 他は不明 |

判定の順番:
1. 3 つ目がマイナスなら、すべてマイナス（マイナスはプラスの後ろに並ぶ）
2. 元から持つスキル以外のプラスが上限（5 − 元から持つスキルの数）に達していて、コストが 3 つ目以下の
   元から持つスキル（写っていないもの）も無ければ、すべてマイナス
3. 写っていない分を「プラス k 個（各 +1、コスト 3 つ目以下）＋写っていない元から持つスキルのマイナス m 回」
   として、ありうる組み合わせを抽選の仕様で調べる（抽選テーブルが「なし」なら行わない）
   - k ≥ 1 の組み合わせがどれも作れなければ、すべてマイナス
   - m = 0 の組み合わせがどれも作れなければ、マイナスが 1 個以上
   - どの組み合わせも作れなければ仕様違反（1・2 で決まった場合も確かめる）

元から持つスキルが未入力なら、すべて「不明」。これまでの結果画面２ 597 件は、すべてマイナス 596 件・
マイナスが 1 個以上 1 件（switch2 の 2026092422294100: 激昂・火事場力・ひるみ軽減 各 +1、防御 -5）。
すべてマイナスと確定した行は、コスト（マイナスは含めない）とスキル欠けも正しい値になる。
